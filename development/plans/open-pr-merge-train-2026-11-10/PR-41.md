### What the patch does

With no host view yet, `setContentView:` gives the view the content rect, as AppKit
documents ("The view object is resized to fit precisely within the content area of the
window"). With a host, `ak_attach` still sizes it from the host's bounds. The
regression it removes: a view made by `-[NSView init]` stayed 0×0 until the window was
on screen, so a guest that sizes its window right after `setContentView:` read
`convertSizeToBacking:{0,0}`, clamped to 320×240, and grew its height for seconds — a
320-wide `CAMetalLayer` frame and a 320-wide render target.

The contributor's device evidence (an iPhone Air, not on the test matrix) is not carried
as evidence. It is replaced by a test that runs on the matrix, and by the External-JIT
render below.

### Evidence

Focused test, `wolkaraforever/tools/test_appkit_content_view.sh` →
`wolkaraforever/AppKit/tests/test_appkit_content_view.m` (overlaid at
`tests/test_appkit_content_view.m`). It asserts:

1. pre-host: an `NSView` from `init` is 0×0, and `setContentView:` on a 320×240 window
   makes it exactly `{0,0,320,240}`; a 912×420 window and a view made with its own frame
   get `{0,0,912,420}`;
2. `convertSizeToBacking:` of that size is the size × `backingScaleFactor`, non-zero, and
   round-trips through `convertSizeFromBacking:`;
3. eight repeats of the client's sizing pass (convert, `setContentSize:`) are a fixed
   point — the window stays 912×420, so it cannot crawl upward;
4. hosted: with a host attached, `setContentView:` and a host bounds change give the view
   the host's bounds (912×420), the layer frame and `contentsScale` follow, and the
   drawable size is 912×420×scale;
5. `ak_hostBoundsChanged:CGRectZero` is never adopted — the last real size stays, so a
   layout pass before the host has a size cannot make a zero-size target;
6. with a host, the host's bounds win over the window's own content rect (1024×768, not
   320×240).

#### The test iPad: External JIT entry is killed by code signing

The same test bundle (`local.wolkaraforever.johnklock.test`, development-signed with both
memory capabilities, built at `3fca304`) on the test iPad — iPad Pro 12.9-inch (5th
generation), iPadOS 27.2:

```text
[host] execution mode=external-jit source=argument
[debugger] nothing has prepared this process; not trapping
[native] arena prepared outside this app address=0x108490000 size=99532800
[native] arena protection 0x5
[native] arena ready base=0x108490000 slide=0x8490000
[native] entering original initializer preferred=0x10340219c native=0x10b89219c
```

and then the process is killed: crash report `TolkaraDiagnostics-2026-11-11-151618.ips`,
`EXC_BAD_ACCESS`, termination `CODESIGNING / Invalid Page`, at `0x000000010b89219c` —
the address the initializer was entered at. No enabler was attached: StikDebug is
installed and paired, but its `stikjit://` route is driven on the device and nothing in
this repository can drive it from the Mac. The app therefore mapped its own arena,
`da_entry_allowed` accepted a mapping that is executable but not signed, and iOS killed
the first guest instruction. That is a finding about the External JIT route itself, not
about this patch — 0054 never ran, because the guest died before any AppKit call. Tracked
as R-013 with a proposal: the External JIT route must refuse a self-mapped arena that no
enabler prepared. **The plan's device rendering step is therefore not met, and is not
claimed.**

The image the launcher picked as its default app in the test container was an imported
copy of *World of Warcraft Forever* (test data from the earlier External JIT work), so
that was the image the kernel killed, at its first instruction; no application
instruction executed. The launcher's own index repair ran on that test copy before entry,
as designed. The stable installation was never the target: `pilot.sh state` reads the same
before and after (app running, 0 update writes, 0 error files, 25 crash reports, newest
2026-10-14). The device was left on the launcher's normal home page — **Ready to play**,
1.60.170888, Checked 15:27.

### Risks

- A guest that relied on a 0×0 content view before showing its window now sees the content
  size. That is AppKit's behaviour.
- On iPad the window is usually hosted before the guest sizes it, so the patch is
  invisible there; the pre-host path is the one the focused test proves.
- External JIT on hardware cannot execute guest code in this configuration (R-013);
  nothing in this PR depends on it.
